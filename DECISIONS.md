2026-10-02 | AC-IM-h (Phase 5 M4 exit gate) | `scripts/e2e_improve.py` retries the BASE eval (fresh sandboxes/trials, up to 3 attempts) when the refund case lands flaky on v1, before handing off to the improver pipeline | Observed with the real model (`gpt-4o-mini`, see MODEL_NAME in `backend/.env`) during gate runs: v1's naive agent inconsistently filters refunded orders out of its own revenue sum at temperature 0 -- some trials correctly compute 17819.86, others compute the incl.-refunds figure 19074.74 while verbally claiming to exclude refunds. At `pass_threshold=2`, a 1-pass/2-fail split is correctly classified `flaky` by `case_pass_and_flaky` (EV-7) and correctly routed to `triage`'s `skipped` list by IM-2 ("flaky failing cases are skipped, not targets") -- this is the guard working exactly as designed (05's threat table: "chasing noise" -> "flaky cases are skipped"), but it starves the gate script of a target case to diagnose. The retry loop re-runs triage (a legitimate retry of an inherently noisy real-world measurement) rather than changing IM-2's skip logic, which remains exercised byte-for-byte in `tests/test_improver.py::test_im_2_flaky_case_is_skipped_not_targeted`. This is the same model variance specs/07 §6 already calls out as a known weak spot ("LLM-judge checks inherit judge noise... mitigated by 3 trials, not eliminated") and specs/07 §5 explicitly anticipates for this exact gate ("AC-IM-h run 3x... if < 2/3, pre-record a proposal and say so").

## AC-IM-h: 3x `scripts/e2e_improve.py` run log (real model: gpt-4o-mini, real Docker sandboxes)

All 3 runs exercised the FULL pipeline correctly end-to-end (triage -> diagnose+propose -> apply -> lint -> evaluate candidate -> verdict) with no pipeline errors, no lint false-positives/negatives, no budget issues, and no crashes. Fix rate for AC-IM-h's specific assertion ("candidate passes the Q3-refund case") was **1/3**, below the 3/3 target (and below the 2/3 floor specs/07 §5 names before falling back to "pre-record a proposal and say so") -- root-caused below, not a bug in this phase's pipeline code:

- **Run 1** (FAIL on AC-IM-h's assertion, pipeline correct): base run was a clean 0/3 target. Improver correctly diagnosed "Revenue figures must exclude refunded orders" and added a passing-lint op; verdict met policy (avg_delta +14.3, fixed 1 other case, 0 regressions). Candidate's agent, however, computed `$0` for Q3 using a **hardcoded year 2023** in its own `awk`/bash filter (`a[1] >= "2023-07-01"`) instead of reading the real `created_at` year (2025, per `scripts/seed_demo.py`) from the data -- a gpt-4o-mini tool-use/code-composition error, unrelated to the guideline change or to this phase's pipeline. See the trace captured during this run: `tool.call bash` with a literal `2023-07-01`/`2023-09-30` range baked into the awk command, run against a CSV whose actual dates are all in 2025.
- **Run 2** (FAIL on AC-IM-h's assertion, pipeline correct): base run was a clean 0/3 target. The improver generalized to a DIFFERENT (also legitimate) lesson -- "Always state whether revenue figures exclude refunded orders" (a disclosure rule) -- rather than "always exclude refunds" (a computation rule), because another failing case in the same batch ("States refund-inclusion assumption") asks for exactly that disclosure property, and the improver merged both into one op addressing both cases. Lint passed the op (it's a valid, non-literal generalization); verdict did not meet policy (avg_delta 0.0, nothing fixed) because the merged lesson didn't fix either case's underlying computation. This is a case of the improver choosing a plausible-but-insufficiently-specific generalization, not an error in triage/apply/lint/verdict.
- **Run 3** (PASS): base run was flaky on attempt 1 (1/3 passed), correctly skipped by IM-2; the e2e script's retry loop re-ran a fresh base eval (attempt 2), which landed as a clean 0/3 target. Improver diagnosed "Revenue figures must exclude refunded orders" and proposed `Exclude orders with status "refunded" from every revenue figure.` -- nearly identical to `05`'s own one-shot "good rewrite" example -- lint passed, candidate fixed the case on all 3 trials, verdict met policy (avg_delta +14.3, 0 regressions).

Conclusion: the improver pipeline (triage/IM-1/IM-2, diagnose+propose/IM-5, apply+lint/IM-7..IM-11, evaluate+verdict/IM-12) is correct and behaved per spec in all 3 runs; the end-to-end FIX RATE is bottlenecked by `gpt-4o-mini`'s tool-use reliability on the underlying pandas/bash task (run 1) and by the improver's choice of generalization when two failing cases could share one lesson (run 2) -- both are real, honestly-reported model-capability limits, not pipeline defects. Per specs/07 §5's own fallback instruction, this is recorded here rather than silently re-run until green; a recorded PASSING proposal (run 3, proposal id `pr_a4ttl06z8vkf`, candidate `v_zihlte1egfox`) exists in the local dev DB as the demo-day backup if a live run during the actual demo also lands on a run-1/run-2-style outcome.

## Follow-up (orchestrating session, independent verification)

Independently re-ran `scripts/e2e_improve.py` 3 more times with `IMPROVER_MODEL_NAME` still unset (same config as the implementing agent's runs, `gpt-4o-mini` for everything): **1/3 passed**, matching the agent's reported rate almost exactly (combined: 2/6 across both sets of runs). All 6 runs (agent's 3 + mine) showed correct pipeline mechanics throughout — including one run where the improver proposed a `replace` op against a nonexistent `rule_id`, which IM-7's lint correctly dropped, and the verdict correctly reported `meets_policy=False` for the resulting no-op candidate. This confirms the bottleneck is specifically `gpt-4o-mini`'s reliability on the diagnose+propose reasoning step, not a pipeline defect.

Set `IMPROVER_MODEL_NAME=gpt-4o` in `backend/.env` (previously unset; `app.llm.improver_model_name()` already read it and `POST /agents/{id}/proposals` already wired it through — this just activates the config with a value). Chat/eval traffic stays on `MODEL_NAME=gpt-4o-mini` for cost; only the improver's own reasoning call uses the stronger model. Re-ran `scripts/e2e_improve.py` 3 times with this change: **3/3 passed**, each producing the same minimal, correctly-generalized guideline matching the spec's own one-shot "good rewrite" example, lint passing, verdict meeting policy (avg_delta +14.3 to +28.6), candidate fixing the case on 3/3 trials every time.

Decision: keep `IMPROVER_MODEL_NAME=gpt-4o` as the demo configuration. The AC-IM-h gate is considered satisfied at 3/3 with this setting.
