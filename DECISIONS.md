# Decisions

Format: date | spec ID | what changed | why

2026-10-02 | SB-5 | `GET /health` returns `sandbox_mode: "not-configured"` instead of one of `"docker"` / `"local-unsafe"` | Sandbox detection logic (Docker availability check) is built in Phase 2 (M1, T1.3); T0.1 only needed the field shape to exist. Will update to real detection when `DockerSandbox`/`LocalSandbox` land.
2026-10-02 | T0.1 | Backend venv created with Homebrew Python 3.11.14, not the system Python 3.9.6 | System Python is too old for current SQLModel/FastAPI; 3.11 also matches the `agentplat-sandbox` image's `python:3.11-slim` base (specs/02-agent-runtime.md SB-1), so dev and sandbox stay aligned.
2026-10-02 | RT interfaces | `run_turn(...)` takes an added `llm: LLM` keyword not listed in specs/02-agent-runtime.md's `Interfaces` signature | The runner must call some `LLM.chat(...)` and the spec's signature has no way to supply one (no `llm` param, and `version` doesn't carry an LLM instance per specs/01-data-model.md); omitting it would force a hidden global/default provider inside the runner, which breaks MG-2's spirit (provider choice stays a caller concern, same as `FakeLLM` vs `OpenAICompatLLM` in tests) and determinism (specs/07 §1). All other parts of the given signature (version, history, sandbox, emit, source) are unchanged.
2026-10-02 | SB-5 | Resolved: `GET /health` now reports real `sandbox_mode` (`"docker"` / `"local-unsafe"`) via `app.sandbox.docker_available()` (Docker daemon ping at startup), replacing the Phase 1 `"not-configured"` placeholder noted in the first SB-5 entry above.
2026-10-02 | CD-5, CD-6, CD-7 | Chat orchestration (sandbox-per-conversation registry, run-in-progress tracking, SSE pub/sub) lives in a new `backend/app/chat_runtime.py` module rather than in `app/services.py` or inline in `app/main.py` | `app/services.py` (Phase 1) is pure DB CRUD with no process-lifetime state; background tasks, in-memory sandboxes, and per-run SSE subscriber queues are a different kind of thing (in-memory, single-process orchestration) and mixing them into the DB-only service layer would blur that boundary. `specs/03-chat-and-deploy.md` doesn't name a specific module for this, so this is an implementation-structure choice, not a behavior deviation — all CD-4..CD-8 requirements are met as specified.
2026-10-02 | 02-agent-runtime.md Events | The `run.started` SSE event's embedded `"run_id"` field (set inside `app/runner.py`'s `run_turn`, e.g. `"r_108e988c0"`) does not match the actual `Run.id` used in the `/runs/{id}/events` URL and in `POST /conversations/{id}/messages`'s `{run_id}` response (e.g. `"run_cj09n0i95ouj"`, generated by `app/chat_runtime.py` via `new_id("run")` before the DB row exists) | `run_turn`'s internal `run_id = f"r_{id(history):x}"` (specs/02-agent-runtime.md line 105) is a local placeholder with no way to receive the caller's real run id (the interface signature in `02` has no `run_id` parameter), and `app/runner.py` was left untouched per this phase's instructions (no bug blocking the phase). This does not affect any P0 requirement or acceptance criterion: callers always learn the real run id from `POST /conversations/{id}/messages`'s response and use that in the `/runs/{id}/events` URL; the mismatched id only appears as a cosmetic field inside the first streamed event's payload. Flagging here in case a later phase wants `run_turn` to accept an optional `run_id` override.
2026-10-02 | CD-1 (data-analyst template) | `data-analyst` template's `orders.csv` is generated by importing and calling `scripts/seed_demo.py`'s `generate_rows()` directly (via a `sys.path` insert in `app/templates.py`), rather than duplicating the generator or shelling out to the script | Spec says the template's files "include orders.csv" seeded via `scripts/seed_demo.py`; importing the existing deterministic generator keeps the demo data identical everywhere (template-created agents, `scripts/smoke_runner.py`, `scripts/seed_demo.py` itself) with zero duplication, at the cost of a `sys.path` import across the `backend/` / `scripts/` boundary (acceptable for this single-repo, non-packaged demo).
2026-10-02 | EV-5 (Phase 4, own bug caught before merge) | First draft of `app/evals.py`'s eval-trial sandbox creation did not seed `version.files` into the fresh per-trial sandbox before calling `run_turn` | Found while running `scripts/smoke_evals.py`: every data-dependent case (row count, top-3-products, revenue) failed on the very first real run because the sandbox had no `orders.csv` at all, not because the model answered wrong. Root cause: `app/chat_runtime.py`'s `get_or_create_sandbox` seeds `version.files` for chat conversations, but the new eval executor built its own fresh-sandbox-per-trial path (EV-5) and that seeding step was missed. Fixed by adding `app.evals._seed_sandbox_files(sandbox, version)`, called right after `sandbox_factory()` in `_run_one_trial`, mirroring `chat_runtime`'s logic exactly (same `read_file_bytes` + `sandbox.seed_file` calls). No spec file changed; this is a self-caught implementation bug in this phase's own new code, not a deviation from `04`.
2026-10-02 | 01-data-model.md runs table ("conversation_id ... Null for eval trials") | First draft of the eval executor generated an `EvalResult.run_id` value (`new_id("run")`) without ever inserting the corresponding `runs` row | The `runs` table's own doc comment implies eval trials get real `Run` rows (`conversation_id` nullable "for eval trials"), and `eval_results.run_id` is a real FK to `runs.id` per `01-data-model.md`. Fixed by adding `app.evals._persist_trial_run(...)`, called from `_run_one_trial` right after `run_turn` returns (and also on the EV-8 exception-backstop path, with `status="failed"`), so every `EvalResult.run_id` now points at a real `runs` row with that trial's actual `trace`/`final_answer`/`status` — needed both for spec compliance and so a human (or `scripts/smoke_evals.py`) can inspect what a trial actually answered. Because trials run concurrently under a shared `asyncio.Semaphore`, `_persist_trial_run` takes an explicit `engine` (threaded through `execute_eval_run`/`run_eval_run`, defaulting to `app.db.engine`) and opens its own short-lived `Session` per trial, rather than sharing one session across concurrent trial tasks.
