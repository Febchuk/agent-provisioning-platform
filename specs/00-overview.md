# 00 — Overview

## 1. Problem

Teams want internal agents that (a) can run code and work with files, (b) can be used by people other than their creator, and (c) get better at their job over time **in a way the owner can see and trust**. Most agent tools stop at (a) and (b). Improvement is either manual prompt fiddling or an opaque self-rewrite.

## 2. Users

| Persona | Who | Needs |
|---|---|---|
| **Owner** (primary) | Engineer who builds an internal agent | Fast setup, visible traces, a measured and reviewable way to improve the agent |
| **Teammate** (secondary) | Non-technical colleague who uses the agent | A simple chat, a cheap way to say "that was wrong" |

Confirmed with interviewers: engineer builds, non-technical teammates use. Chat UI first, API second. Improvements are **proposed as a diff and approved by the owner**, never applied silently.

## 3. Goals and success criteria

| ID | Goal | Measured by |
|---|---|---|
| G-1 | A first-time owner can create and deploy an agent quickly | Time from "New agent" to working share link ≤ 3 min in the validation run |
| G-2 | Teammates can use an agent without seeing config | Share page works with no login, no owner controls visible |
| G-3 | Agents measurably improve from feedback | Demo: a teammate correction → eval case → proposal that fixes it, with score shown before/after |
| G-4 | Improvements are trustworthy | Every proposal shows diff, per-case results, policy verdict, and generalization on hidden cases |
| G-5 | Not locked to one model provider | Model endpoint is configurable (`base_url`); no provider-specific code in the runner |

## 4. Scope

### In scope (P0 — required for the demo)

- Create an agent from a template; edit system prompt, learned guidelines, tools, workspace files.
- Immutable versions; deploy = move a pointer; rollback.
- ReAct runner with tools: `bash`, `read_file`, `write_file`, `edit_file`, `list_files`.
- Sandbox: one Docker container per conversation; fresh container per eval trial.
- Multi-turn chat with live step events over SSE; full trace persisted per turn.
- Public share page per agent (serves the deployed version).
- Thumbs up/down + free-text correction on any agent turn.
- Owner turns feedback into an eval case (drafted by an LLM, confirmed by a human).
- Eval cases with 3 check types: `contains`, `python_assert`, `llm_judge`; axes; pinned flag.
- Eval executor: N=3 trials per case, pass = ≥2/3.
- Per-agent promotion policy: min avg improvement, max regressions per axis, pinned never regress.
- Improver: triage, diagnose, structured ops on guidelines, literal lint, size budget.
- Proposal review: diff, per-case matrix, verdict, accept / accept & deploy / reject, change note (required on policy override).
- Seed script for the demo agent (Revenue Analyst + `orders.csv` + starter cases).

### In scope (P1 — if time allows, in this order)

1. Hidden sibling cases generated on case confirmation; generalization score on proposals.
2. API endpoint with bearer API keys.
3. Owner playground in Studio (until then, owner uses the share page to test).
4. Multiple candidate proposals (3) with best-by-policy selection.
5. Open-source model behind the same `base_url` (e.g. vLLM).

### Out of scope (explicitly not built — say so in the walkthrough)

| Item | Why it's out |
|---|---|
| User accounts, auth for owner screens, multi-tenancy, RBAC | Single local owner is enough to demonstrate the product loop |
| Production-grade sandbox security (gVisor/Firecracker, egress policies) | Container is not a security boundary; acknowledged risk |
| Token-by-token streaming | Step-level events give the same "it's working" feel for less code |
| Visual / no-code agent builder, multi-agent orchestration | Not needed to show create → deploy → improve |
| Cron / webhook triggers, Slack integration | Interviewers prioritized chat UI, then API |
| Automatic promotion without owner approval | Explicitly rejected — trust |
| Fine-tuning / weight updates | Improvement is via versioned instructions; cheaper, reviewable, reversible |
| Postgres, queues, horizontal scaling | SQLite + asyncio; listed as "what breaks first" |
| Cost tracking / billing, rate limiting | Not part of the brief |

## 5. Assumptions

- A-1 Interviewers provide an LLM API key for an OpenAI-compatible endpoint (or one is reachable via a compatible proxy).
- A-2 Docker is available on the demo machine. Fallback: subprocess sandbox in a temp dir (flagged unsafe in UI).
- A-3 One owner, a handful of teammates, < 100 eval trials per proposal.
- A-4 The demo dataset is synthetic and generated by our seed script (deterministic seed).

## 6. Constraints

- 5 hours total, including demo prep.
- Stack: FastAPI + SQLModel/SQLite (backend), Next.js App Router + Tailwind (frontend), OpenAI Python SDK with configurable `base_url`, Docker SDK for Python.
- Tests: pytest + httpx; a scripted `FakeLLM` makes runner/improver tests deterministic.

## 7. Glossary

| Term | Meaning |
|---|---|
| Agent | Named container of versions; has one deployed version |
| Version | Immutable snapshot: system prompt, guidelines, tools, model, limits, files |
| Guidelines | Structured list of rules (`skills.md` when rendered) the improver edits |
| Turn / Run | One agent response to one user message, possibly many tool steps |
| Trace | Ordered list of events for a run |
| Eval case | Conversation prefix + check; has an axis; may be pinned or hidden |
| Trial | One execution of one case on one version |
| Proposal | Candidate version + evals + verdict, awaiting owner decision |
| Sibling | Hidden case generated from a confirmed case to test generalization |

## 8. Milestones (time boxes)

| M | Time | Exit gate (see `07`) |
|---|---|---|
| M0 | 0:00–0:20 | Repo, env, seed data, `FakeLLM`; `pytest` runs |

| M2 | 1:30–2:15 | Versions, deploy, conversations, SSE; `scripts/smoke_chat.sh` passes |
| M3 | 2:15–3:15 | Feedback → cases → evals → policy/verdict; verdict unit tests pass |
| M4 | 3:15–4:00 | Improver + proposal accept/reject; end-to-end improvement on seed agent |
| M5 | 4:00–4:30 | Frontend screens wired; validation run V-1 |
| M6 | 4:30–5:00 | P1 items only if M5 passed; rehearse demo |

**Rule:** a milestone does not start until the previous exit gate passes. If behind at 3:15, cut P1 entirely and the Versions screen down to a list.
